## 2. NON-NEGOTIABLE INTEGRITY RULES

- No fabricated data: no invented `aggregateRating`, review counts, user counts, "sub-millisecond" claims, ratings, volumes, rankings or awards. The home-page testimonials array stays empty.
- Every keyword added must carry evidence in the research log: source (tool/URL), country, language, observed volume or SERP signal, date. No evidence → do not use it.
- Never create a localized country page without verified native search demand. Non-localized countries fall back to English with `x-default`. No hard IP redirects.
- Localization = native transcreation from local queries, never translation of English copy. Only the locales that already exist (`ko`, `ja`, `de`, `pt`, `es`, `fr`) may be extended, and only where demand is verified. Previously measured: most non-English reaction/cognitive demand is ~zero; Korean and Japanese are the strongest. New locales only if live research proves demand AND the standard's gate passes.
- Schema must match visible on-page content exactly (FAQ in JSON-LD == FAQ in HTML). Verify rendered HTML, not source: undeclared props have silently dropped guides/FAQs before.
- Keep the visual design direction. Fix copy and structure, not chrome.
- Scientific claims need real citations already present in `lib/drillSources.js` or a verifiable source; otherwise soften or remove the claim.

## 4. PHASE B — LIVE RESEARCH (per page, per target market)

Primary goal of this phase: find HIGH-DEMAND + LOW-COMPETITION keywords, per country, in the native language, using LIVE web research. Bing Webmaster and Search Console are optional extras, never required and never the main source.

### B1. Live research tools (use all that apply; do not rely on memory or the repo's old numbers)

- `WebSearch` (extended mode for niche/local queries) and `WebFetch` on live SERPs, competitor pages, forums and communities.
- Google Trends (`trends.google.com/trends/explore?geo=<CC>&q=<term>` and its related queries/topics) — interest over time and rising queries, per country.
- Search autocomplete/suggest, per country and language (Google `suggestqueries.google.com/complete/search?client=firefox&hl=<lang>&gl=<CC>&q=<seed>`, Bing and YouTube suggest, Naver/Yahoo! Japan suggest where reachable). Expand each seed with a–z and question words in the native language.
- SERP features per query: People Also Ask, related searches, AI Overview/answer text, featured snippet, video/forum blocks.
- Local engines and communities: KR Naver + DC Inside; JP Yahoo! Japan + 5channel; DE Google.de + computerbase; BR Google.com.br; ES/LatAm Google.es/.mx; FR Google.fr; plus Reddit and YouTube titles/comments in each language. Adjust per page topic.
- Optional only if available in the environment: `BING_API_KEY` → `scripts/bing/bing.py` (`keyword`, `related`); GSC creds → `scripts/gsc/gsc.py`. If missing, skip silently and log "API unavailable". Never ask for keys.

### B2. Countries covered

- Every country/language that already has a page tree in `app/<loc>/` (`ko`, `ja`, `de`, `pt`, `es`, `fr`) gets its own local research per page, using that country's engines, language and trends. No reuse of English keywords, no translation.
- English pages: research US, UK, CA, AU, IN (and other English markets showing demand) and pick the best shared phrasing; note country differences in the log.
- Refresh trends for each country per page: rising vs falling queries, seasonal/launch-driven spikes, new game/title terms (e.g. new FPS releases players are searching with). Record the date.
- A NEW country page is created only when live evidence shows real, sustained native demand AND the Standard's gate passes. Otherwise the country falls back to English with `x-default`. List such countries as "demand not verified" in the report.

### B3. Keyword scoring (low competition + high demand)

For every candidate phrase, record proxies in the log, then score:

- Demand signals (more = better): appears in autocomplete for that country; Google Trends interest/rising; related-search and PAA presence; community/forum threads asking it; Bing/GSC volume if available.
- Competition signals (fewer = better): top-10 results are weak (forums, Q&A, thin pages, generic homepages, PDFs); no page's title exactly matches the query; few tools/pages truly satisfy the intent; low-authority domains ranking in top 5; SERP in a different language than the query; allintitle-style exact-match check shows few results.
- Intent fit: the phrase must match what the page actually delivers (a drill/tool/test/guide). No clickbait.
- Score each 1–5 for demand, competition (5 = easy), intent fit. Pick the primary keyword with the best (demand × ease) among intent-fit phrases; adopt 3–8 secondary/long-tail phrases and the question-form phrases for AEO.
- Volumes from web research are PROXIES. Never state invented numbers. Label every figure as `measured (source)` or `proxy (signal)`. If only proxies exist, say so.
- Reject phrases with no evidence of demand. Reject phrases that are high-competition with no angle to win.

### B4. Per-page capture

- Primary query, secondary/long-tail queries (native language), question phrases, search intent, top-5 SERP competitors and their gaps, PAA/AI-answer patterns, entities to cover, trend notes with date, scores from B3, final decision and why.
- Save raw findings to `docs/seo/research/<locale>/<slug>.md`. Commit it with the page.

## 5. PHASE C — ONE PAGE AT A TIME (the loop)

Take the first `pending` row in `docs/seo/PAGE_QUEUE.md`. Set it `in-progress`. Do not start another page until this one is committed and pushed.

1. Research (Phase B) → write the research file.
2. Run the 30-point checklist against the page; list failures.
3. Fix using the winning low-competition/high-demand keywords from B3 (the page's own locale, never borrowed from another country), in this order:
   - Title (≤ ~60 chars, primary query first, unique), meta description (≤ ~155, intent-matching, unique), canonical, hreflang.
   - H1 matches the primary query naturally; H2s map to secondary queries and People-Also-Ask questions.
   - AEO: a direct 40–60 word answer block near the top for the main question; question-style H2s; concise definitions; honest, citable facts; FAQ section with real, distinct questions (localized drills: exactly 10 bespoke FAQs).
   - GEO: clear entity naming (SkillDrills, the drill, the skill measured), consistent facts across pages, `WebApplication`/`FAQPage`/`BreadcrumbList` JSON-LD that mirrors visible content, plain-text `llms.txt` entry, cited sources, no unverifiable superlatives.
   - Internal links with descriptive anchor text via the existing `RelatedDrills` / `lib/drillSeo.js` mesh (meta keywords are inert; anchor text is the lever).
   - Localized pages: native phrasing only, full depth, no truncation, no numbered placeholder FAQs, no duplicated meta descriptions.
4. Verify on rendered HTML (start `next dev`, fetch the URL, inspect): title, meta, canonical, hreflang set, single H1, FAQ present in HTML, JSON-LD parses and matches visible text, no `aggregateRating`. Confirm the drill itself still loads (route returns 200, no console errors) — do not alter it.
5. Grep guard before commit: `aggregateRating`, `sub-millisecond`, `Q4`–`Q10` placeholders, duplicate meta descriptions.
6. Commit to `main` with message `seo(<locale>/<slug>): <what>`; `git pull --rebase origin main`; `git push origin main`.
7. Update the queue row: status `done`, commit sha, research link. Commit that too.
8. Next page.

Batching rule: once a pattern is proven on one page, similar pages may be done faster, but each still gets its own research evidence and its own commit.
