## 0. SCOPE (HARD LIMITS)

- Change ONLY search-facing surface: `<title>`, meta description, canonical, hreflang, Open Graph, H1/H2 copy, intro/about/guide prose, FAQ content, JSON-LD, internal links/anchor text, `app/sitemap.js`, `app/robots.js`, `app/llms.txt/`, `lib/drillSeo.js`, `lib/searchDrills.js`, docs.
- NEVER touch drill mechanics: game loops, canvas/render code, scoring, difficulty, timers, audio, flash, settings toggles, `lib/drill*.js` runtime helpers (except `lib/drillSeo.js`), hooks, or any `*Client.js` logic beyond SEO copy/schema props.
- If an SEO fix needs a gameplay-code edit: skip it, log it in `docs/seo/PAGE_QUEUE.md` under Blockers, move on.
- Follow `CLAUDE.md` and `AGENTS.md`: point-wise output, no explanatory comments in new code, smallest correct change.
- Never run `npm run build` (postbuild pings live search engines). Use `npx next build` only for a compile check, or `next dev` for rendered-HTML checks.
- Vercel is DISCONNECTED from GitHub on purpose. Pushing to `main` does not deploy. Do not reconnect Vercel, do not create deploy hooks, do not call Vercel tools.
- Work directly on `main`. No feature branches. `git pull --rebase origin main` before every push.

## 1. BINDING STANDARDS (read first, in this order)

1. `docs/seo/GLOBAL_PAGE_SEO_AEO_GEO_STANDARD.md` — 14-step SERP audit, 30-point checklist, 5-phase protocol, Pre-Coding Gate.
2. `docs/seo/NO_TRANSLATION_NATIVE_SEARCH_MANDATE.md` — no machine translation; native-keyword transcreation only; 10 bespoke FAQs per localized drill.
3. `docs/SEO_PROGRESS.md` and `docs/seo/INTERNATIONAL_STRATEGY.md` — history, what was already measured, what failed.
4. `docs/seo/AGENCY_PLAN_AUDIT.md` — what was rejected; do not re-propose it.

## 2. NON-NEGOTIABLE INTEGRITY RULES

- No fabricated data: no invented `aggregateRating`, review counts, user counts, "sub-millisecond" claims, ratings, volumes, rankings or awards. The home-page testimonials array stays empty.
- Every keyword added must carry evidence in the research log: source (tool/URL), country, language, observed volume or SERP signal, date. No evidence → do not use it.
- Never create a localized country page without verified native search demand. Non-localized countries fall back to English with `x-default`. No hard IP redirects.
- Localization = native transcreation from local queries, never translation of English copy. Only the locales that already exist (`ko`, `ja`, `de`, `pt`, `es`, `fr`) may be extended, and only where demand is verified. Previously measured: most non-English reaction/cognitive demand is ~zero; Korean and Japanese are the strongest. New locales only if live research proves demand AND the standard's gate passes.
- Schema must match visible on-page content exactly (FAQ in JSON-LD == FAQ in HTML). Verify rendered HTML, not source: undeclared props have silently dropped guides/FAQs before.
- Keep the visual design direction. Fix copy and structure, not chrome.
- Scientific claims need real citations already present in `lib/drillSources.js` or a verifiable source; otherwise soften or remove the claim.

## 3. PHASE A — AUDIT SINCE LAST DEPLOY (once, then persist)

1. `git log --since="14 days ago" --stat origin/main` and `docs/` — list pages/routes/metadata changed or added in the last ~2 weeks. Those are the first-priority audit targets.
2. Inventory every indexable URL: derive from `app/sitemap.js`, `lib/drillsRegistry.js`, `lib/drillCatalog.js`, and every `app/<loc>/` tree. Include: home, `/drills`, 8 category hubs, every drill, `/about`, `/search`, `/privacy`, `/terms`, `/delete-account`, localized routes (`LOCALIZED_ROUTES`).
3. Create `docs/seo/PAGE_QUEUE.md`: one row per URL — `URL | locale | type | priority | status (pending/in-progress/done/blocked) | research-log link | commit sha`.
4. Priority order:
   1. Pages that changed in the last 2 weeks.
   2. `/`, `/drills`, category hubs.
   3. Drills ranked by existing demand (Bing is the larger channel: use `docs/` reports, `scripts/bing/baseline/`, `scripts/keywords/`).
   4. Remaining English drills.
   5. Localized pages with verified demand.
5. Site-wide technical pass (one commit): canonical correctness, hreflang reciprocity and `x-default`, sitemap `lastmod` honesty, robots, `llms.txt`, duplicate titles/descriptions, missing H1, orphan pages, redirect chains, structured-data validity. Log findings; fix only SEO-surface files.

## 4. PHASE B — LIVE RESEARCH (per page, per target market)

Use live tools; do not rely on memory or the repo's old numbers:

- `WebSearch` (extended mode for niche/local queries) and `WebFetch` on real SERPs and competitor pages.
- Per-country sources: Google (country domain) + that market's engines/communities — KR: Naver, DC Inside; JP: Yahoo! Japan, 5channel; DE: Google.de, computerbase; BR: Google.com.br; ES/LatAm: Google.es/.mx; FR: Google.fr. Adjust per page topic.
- If `BING_API_KEY` is available in the environment, use `scripts/bing/bing.py` (`keyword`, `related`, `pagequeries`). Otherwise skip Bing API; do not ask for keys; note "Bing API unavailable" in the log.
- If GSC credentials are unavailable (they are local-only, gitignored), skip GSC; note it.
- For each page capture: primary query, 3–8 secondary/long-tail queries in the native language, search intent, top-5 SERP competitors and their gaps, People-Also-Ask / AI-answer patterns, entities to cover.
- Prefer high-intent, low-competition ("soft SERP") phrases. Reject phrases with no evidence of demand.
- Save raw findings to `docs/seo/research/<locale>/<slug>.md` (what was searched, what was seen, decisions). Commit it with the page.

## 5. PHASE C — ONE PAGE AT A TIME (the loop)

Take the first `pending` row in `docs/seo/PAGE_QUEUE.md`. Set it `in-progress`. Do not start another page until this one is committed and pushed.

1. Research (Phase B) → write the research file.
2. Run the 30-point checklist against the page; list failures.
3. Fix, in this order:
   - Title (≤ ~60 chars, primary query first, unique), meta description (≤ ~155, intent-matching, unique), canonical, hreflang.
   - H1 matches the primary query naturally; H2s map to secondary queries and People-Also-Ask questions.
   - AEO: a direct 40–60 word answer block near the top for the main question; question-style H2s; concise definitions; honest, citable facts; FAQ section with real, distinct questions (localized drills: exactly 10 bespoke FAQs).
   - GEO: clear entity naming (SkillDrills, the drill, the skill measured), consistent facts across pages, `WebApplication`/`FAQPage`/`BreadcrumbList` JSON-LD that mirrors visible content, plain-text `llms.txt` entry, cited sources, no unverifiable superlatives.
   - Internal links with descriptive anchor text via the existing `RelatedDrills` / `lib/drillSeo.js` mesh (meta keywords are inert; anchor text is the lever).
   - Localized pages: native phrasing only, full depth, no truncation, no numbered placeholder FAQs, no duplicated meta descriptions.
4. Verify on rendered HTML (start `next dev`, fetch the URL, inspect): title, meta, canonical, hreflang set, single H1, FAQ present in HTML, JSON-LD parses and matches visible text, no `aggregateRating`. Confirm the drill itself still loads (route returns 200, no console errors) — do not alter it.
5. Grep guard before commit: `aggregateRating`, `sub-millisecond`, `Q4`–`Q10` placeholders, duplicate meta descriptions.
6. Commit to `main` with message `seo(<locale>/<slug>): <what>`; `git pull --rebase origin main`; `git push origin main`.
7. Update the queue row: status `done`, commit sha, research link. Commit that too.
8. Next page.

Batching rule: once a pattern is proven on one page, similar pages may be done faster, but each still gets its own research evidence and its own commit.

## 6. CONCURRENCY AND SAFETY

- Other agents/editors may touch this repo. Never revert changes you did not make. If a rebase conflicts in a non-SEO file, keep theirs.
- Never commit secrets (`.env`, `*.json` tokens, `scripts/bing/.bing-key`). Never print keys.
- Never force-push. Never delete branches. Never rewrite history.
- If blocked (structural issue, missing demand evidence, needs gameplay change): stop that page, mark `blocked` with reason, continue with the next.

## 7. STOP CONDITIONS

- Queue fully `done` or `blocked`.
- Or context/time runs low: finish and push the current page, make sure `PAGE_QUEUE.md` is current, then stop.

(only if the whole queue is complete and verified; otherwise report `STATUS: PARTIAL` with what remains.)
